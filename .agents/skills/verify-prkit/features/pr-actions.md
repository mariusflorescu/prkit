# PR actions

The expanded and compact PR headers offer the same three things: Review, the one action the PR's GitHub state calls for, and a More pull request actions menu with the other state changes that apply now. Each action shows once. Editing, labels and reviewers live in Conversation. Every write uses the account bound to the open PR. Merge and branch updates reject a changed head.

## Sub-features

- `header` picks the primary with `primaryPullRequestAction` and the menu with `pullRequestMenuActions` (`packages/contracts/src/pullRequestActionPolicy.ts`, unit-tested). The primary is Resolve conflicts on a conflicting open PR, drafts included, then the first the account may take of Revert when merged, Reopen when closed, Ready for review on a draft, Update branch when behind, Disable or Enable auto-merge, else Merge. When the account may take none of them, the header shows Review and, if anything applies, the menu. Merge, Update branch and Enable auto-merge are split buttons whose arrow opens the method. The menu has a merge group (Merge, Update branch, the one auto-merge action that applies where the repository allows it, Approve workflows on a fork's PR) and a lifecycle group (Ready for review or Convert to draft, Close pull request), without the primary. A merged or closed PR has no menu.
- `lifecycle` converts draft and ready states, closes with confirmation, and reopens.
- `merge` offers merge, squash, and rebase with GitHub's prefilled messages. Method and branch deletion preferences persist per repository.
- `update` merges the base into a behind branch or rebases it onto the base.
- `revert` creates a revert PR and opens it in a new app tab.
- `metadata` edits title and Markdown description (Edit next to the description), labels, and user or team review requests, from Conversation.
- `restricted` keeps a primary that applies but is blocked right now (Merge while GitHub is still checking mergeability) in place, `aria-disabled` and still focusable, with the reason in its tooltip and as its `aria-describedby` description. A menu action that applies but waits (Merge on pending required checks) is disabled the same way. An action the account may never take is left out, from the header and the menu.
- `checks` uses a red icon for failures, amber for pending checks, and green when every displayed check passes. Skipped or neutral checks keep the icon neutral.

## How to get to it (user POV)

- Open a PR from the inbox, a workspace tab, or the PR URL palette.
- Use the primary action or More pull request actions in the header.
- Scroll down to use the same controls in the compact header.
- In Conversation, use Edit title and description, Edit labels, or Edit reviewers.

## Gotchas

- Confirmation dialogs take their accessible name from the heading, such as Merge or Close pull request.
- The confirm holds the head shown when it opened. Retry after a stale-head rejection requires closing and reopening the confirm after reviewing the new head.
- Protected branches, forks, and absent branches cannot be deleted through the merge form.
- Auto-merge needs a plan with it and a requirement that blocks the merge (a required check): GitHub refuses `enablePullRequestAutoMerge` on a clean PR. The fixture has neither, so the happy path runs on the fake GitHub. Fork workflow approval needs a real fork run waiting for approval; no second account may fork the fixture, so that runs on the fake too.
- The fake GitHub keeps every write prkit sends at `GET /__fake/writes` (`fake.writes()`), so a journey checks the request's shape, not only the screen.
- Each fixture PR targets a base branch of its own (`e2e/pr-actions-<slug>-base`, cut from main), so advancing its base, updating its branch and merging it never move main under another run. Cleanup deletes the base with the PR's branch. Base commits use unique files; no force pushes are needed.
- Branch-update journeys need the fixture repository's `allow_update_branch` on (Always suggest updating pull request branches): GitHub returns `viewerCanUpdateBranch: false` when it is off. Every run shares the setting, so the journeys check it (`requireBranchUpdates`) and fail at once when it is off instead of changing it.
- GitHub can recalculate mergeability before REST reports a new head. The changed-head journey polls GitHub until the new head is visible and verifies that the open confirm still holds the previous head.
- A mutation needs GitHub state evidence as well as screenshots. Named frames and videos are under the selected proof output. Copy durable proof into `.e2e/evidence/pr-actions/`.
